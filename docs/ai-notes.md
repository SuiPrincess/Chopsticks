# AI設計ノート — 実験記録

AIEngineの探索設計に関する実験結果の記録。**将来の改善検討時は先にここを読むこと。**
（実験はLinux環境のPython参照実装 `chopsticks_ref.py` で実施。Swift実装とロジック同一を
ルートスコア照合で確認済み）

## 結論サマリ

1. **深さ6以上で実用強度は飽和する。** 現行の反復深化＋持ち時間
   （つよい=200ms/最大10手、鬼=450ms/最大16手）で十分すぎる。
2. **置換表（TT）は移植しない。** ノード数は大幅に削減できるが（下記）、
   製品強度が上がらないため複雑さに見合わない。
3. **ミラー自己対戦は強さの指標として使えない。** このゲームでは
   深さと自己対戦勝率が単調でない（後述の病理）。評価は必ず
   「ランダム＋中位ラダー相当の混成プール」に対する勝率で行うこと。

## 実験1: 置換表のノード削減（2026-07-17）

中盤局面・分割ルールON、反復深化込み:

| 深さ | ベースライン | TT | 比率 |
|---|---|---|---|
| 6 | 1,561 nodes | 1,570 | 101% |
| 8 | 5,620 | 2,938 | 52% |
| 10 | 14,252 | 4,200 | **29%** |

TT実装: キー=(両者の指ベクトル, 手番==AI, attacksUsed)、EXACT/LOWER/UPPERフラグ、
TTベストムーブ先頭化、詰みスコア（±WIN-ply）はply依存のため**保存しない**。
固定深さ・全幅窓でルートスコアがベースラインと84局面で完全一致（正しさ確認済み）。

## 実験2: 深さと強さの関係（同上）

固定深さ同士のミラー対戦（先手交代、n=16）:

- 深さ6 vs 深さ8 → **16-0 で深さ6が勝つ**
- 深さ8 vs 深さ10 → 0-16 で深さ10
- 深さ8 vs 深さ12 → 8-8

→ 単調ではない。循環（千日手）のあるゲームで、探索は60ターン判定を
見ていないため、深読みが判定基準（手数→指数）から乖離した順路を選ぶ
ことがある。ミラー対戦は軌道のわずかな差で全勝/全敗に振れる。

## 実験3: 現実的プールに対する勝率（同上）

相手プール: ランダム20戦 + Lv5相当（40%ランダム＋4手読み）20戦、先手交代:

| 候補 | 合計勝率 |
|---|---|
| 深さ6固定 | 38/40 |
| 深さ8固定 | 37/40 |
| 深さ10固定 | 38/40 |
| ベースライン（25kノード予算） | 40/40 |
| TT（25kノード予算） | 37/40 |

→ 全候補が誤差範囲。**深さを伸ばしても実用強度は上がらない。**

## 将来の改善候補（もしやるなら）

- 強くする方向はほぼ飽和。やるなら「面白くする」方向:
  - レベル別の性格付け（攻撃偏重/防御偏重の評価重み差し替え）
  - あえて人間らしいミスをする「見落としモデル」（低レベルの自然さ向上）
- 60ターン判定を探索に組み込む（turnCountを状態に含め、上限で判定値を返す）。
  ただし現状の実用強度では効果は限定的と予想
- 置換表を再検討する場合は、まず実験3のプール勝率で効果を実証すること

## 毒ルールの退化分析（2026-07-17）

毒（指1本の攻撃で相手の手を即死・相討ち）は、**最適応答の対戦では構造的に退化する**:

- 開始時は全手が指1本 → 全ての合法タップが毒相討ちになる
- どの手も指1本の攻撃で殺せるため、指の本数（マテリアル）が無意味になり、
  最適戦略は「相討ちトレードのパリティ（生存手数の偶奇）」だけで決まる
- 分割で大きい手を作っても毒1発で死ぬため対抗手段にならない

参照実装の鬼AI自己対戦（深さ8）で確認した結果:

| 構成 | 結果 |
|---|---|
| 毒＋2本手（ダブルタップなし） | 先手必敗・2〜3手 |
| 毒＋2本手＋ダブルタップ | 先手2タップ自動勝利 |
| 毒＋3本手＋分割（±爆弾/ミラー） | 先手3タップ勝利 |
| 毒＋3本手＋分割＋ダブルタップ | 後手勝利・3手 |

→ 手数や分割の追加では直らない。**今日の挑戦/今週の試練の生成からは毒を除外**した。
カスタムルール（人間同士の遊び）としては意図的に残している。
おまかせルールは「毒→3本手＋分割」の同伴制約つき。

## 今週の試練のルール構成キュレーション（2026-07-17）

週の試練は「人間が先手・相手は鬼（深さ16探索）」のため、ルール構成の理論値が
そのまま週の成立性を決める。`tools/analysis/exact_solver.py`（60ターン上限・
サドンデス込みの厳密ソルバー）で毒以外の全ルール部分集合×手数×ループ×復活の
44構成を完全解析した結果:

- **標準ルール（特殊なし）は全変種が後手勝ち**。ただし勝ち筋はターン上限まで
  見通す長い筋で、アプリのAI（深さ8〜16・時間制限つき）の地平線外のため、
  ランク戦・フリー対戦の実用性には影響しない
- **ミラーを含む構成は全滅**（後手必勝か、ミラー×爆弾の「自分の手を4に育てて
  誘爆全滅」による先手2手自動勝利のどちらかに崩壊）
- 採用基準は「**先手勝ち かつ 最適応答で9手以上**」: 後手必勝は鬼相手に
  絶対勝てない週になり、短手数の先手勝ちは自明なチーズになるため

基準を満たした構成のみを `WeeklyChallenge.trials` に採用
（split/bomb/doubleTapの組合せ×手数×ループ×復活）。
最短9手〜33手の幅があり、短い構成は「勝ち筋を探すパズル週」、
長い構成は「地力で殴り合うガチ週」になる。

### 追記: 爆弾連鎖のスナップショット意味論（同日の敵対的レビューで発覚）

Swiftの `processBombs` は `for hand in player1.hands + player2.hands` で反復する。
`Hand` はstructなのでこれは**スイープ開始時点の値コピーのスナップショット**であり、
同時に4になった複数の手は「先の爆発のスプラッシュで死んでいても全て爆発する」。
初版ソルバーは生値再スキャン方式でこの点が食い違っており（5,640入力で結果不一致）、
爆弾×3本手の2構成（split+bomb+double）を誤って「先手勝ち12手」と判定していた。
Swift忠実版で再解析すると実際は**後手必勝7手**＝勝てない週になるため採用から削除し、
最終的な採用は**11構成**（爆弾入りは split+bomb×2本手×復活 の2構成のみ）。
ソルバーのprocess_bombsはスナップショット方式に修正済み。
**trials変更時は必ず `tools/analysis/exact_solver.py` を再実行して突合すること。**
